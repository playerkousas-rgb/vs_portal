# Apps Script／Google Sheets 配額（詳細）—— 免費帳號會唔會頂唔住？

> 資料來源：Google 官方〈Quotas for Google Services〉（最後更新 2026-09-03）。
> 所有數字 Google 隨時可以改，呢頁係「幫你估下夠唔夠用」嘅參考。

---

## 1. 兩種帳號

| | 免費（例如 `@gmail.com`） | Google Workspace（學校／機構帳號） |
| --- | --- | --- |
| **每次執行最長**（Script runtime） | **6 分鐘** | **6 分鐘** |
| 自訂函式（試算表公式） | 30 秒／次 | 30 秒／次 |
| **同一個用戶同時執行** | **30 個** | 30 個 |
| **同一個 Script 同時執行** | 1,000 | 更高 |
| 觸發條件總執行時間（時間觸發） | **90 分鐘／日** | 6 小時／日 |
| URL Fetch 呼叫 | 20,000／日 | 100,000／日 |
| 寄出郵件收件人 | 100／日 | 1,500／日 |
| Properties 讀／寫 | 50,000／日 | 500,000／日 |
| 建立試算表 | 250／日 | 3,200／日 |

配額係**逐個用戶計**，由第一次請求起計 24 小時重置。超過就會拋錯，執行即刻停。

---

## 2. 我哋個系統實際用幾多？

**一個旅團（幾十人、一張 Sheet、一支 Apps Script `/exec`）嘅用量：**

| 動作 | 後端做嘅事 | 用量評估 |
| --- | --- | --- |
| 執委開「進度紀錄」（`?action=load`） | 讀 6 個分頁 `getDataRange()` + 讀 1 個 Properties（API Key） | 一次執行約 1–3 秒，**遠低於 6 分鐘** |
| 同步總表（`action=sync`） | 寫十幾個分頁 | 幾秒 |
| 勾進度（`action=save`） | 逐項讀／寫「進度追蹤」 | 勾 30 項 ≈ 幾秒 |
| 全團同時報名 | `appendRow` 加上 `LockService` 排隊 | 30 人同一秒都應付得來（同一用戶上限 30 個同時執行） |
| 審批（`reviewRequest`） | 改 1 行 ＋ 寫 1 行 | 少於 1 秒 |

**關鍵：呢個系統冇用時間觸發（time-driven trigger）**，所以「觸發總執行時間 90 分鐘／日」呢一項根本用唔到（嗰項係計定時自動跑嘅 script，唔係網頁請求）。

---

## 3. 真正要留意嘅三樣

1. **6 分鐘／次**：我哋每次請求都係「讀一版資料」或者「寫一批改動」，正常 1–3 秒。真係要小心嘅係：如果一次過同步成副總表＋幾十張相，或者 Sheet 大到幾萬行，就要考慮分批。
2. **同一時間 30 個執行**：例如「通告一出，全團同一秒撳報名」。所以我哋喺後端寫入路徑加咗 `withLock()`（`LockService`）：多人同時寫會自動排隊，唔會撞到寫壞資料；等唔到鎖（20 秒）都會照做，唔會卡死用戶。
3. **Properties 讀寫 50,000／日**：每次請求會讀一次 `API_KEY`。即係話一日大約可以處理**幾萬次**請求 —— 對一個旅團來講係天文數字。

---

## 4. 頂到幾盡？（實用數字）

保守估計，一個旅團一日：

* 執委開進度頁 50 次 × 3 秒 = 150 秒
* 勾進度 20 次 × 2 秒 = 40 秒
* 團員報名／申報 100 次 × 1 秒 = 100 秒
* 加起上嚟 **每日約 5 分鐘執行時間**，而「觸發 90 分鐘」嗰條線根本唔關事，6 分鐘／次嘅限制亦冇一次接近。

→ **正常運作完全冇問題**。真正容易出事嘅係「寫錯 script 令佢無限迴圈」或者「同一秒幾百個請求」，兩者都唔係我哋個設計會出現嘅情況。

---

## 5. 撞到配額會見到咩／點算

Google 會拋類似呢啲錯誤（我哋前端會顯示「讀唔到後端」）：

* `Script runtime exceeded`（超過 6 分鐘）
* `Script invoked too many times per second for this Google user account.`（一秒內太多次）
* `There are too many scripts running simultaneously for this Google user account.`（同時執行太多）

處理次序：

1. **睇下係唔係循環／重複執行** —— 最常見係自己寫嘅 trigger 或公式出事（我哋冇用）。
2. **等 24 小時**（配額自動重置），或者改用 Google Workspace 帳號（同一支 Script，配額放大幾十倍）。
3. 真係用量大：把「讀」嘅部分加 `CacheService` 快取（例如 load 結果快取 30 秒），或者將歷史資料分頁歸檔。

## 6. 拆細：幾張 Sheet ＋ 幾支 Script（複雜系統嘅做法）

一個 Script 做所有嘢，出事時一齊死、亦難查。所以分工係咁：

| 情況 | 做法 |
| --- | --- |
| **同一份資料** | 一定要**同一張 Sheet**（例：進度追蹤／活動履歷／成員名單 —— 兩個前端共用，唔可以分成兩張再同步） |
| **唔同用途／唔同敏感度** | 分開（例：財務、人事、進度，各自一張 Sheet；各有各嘅權限） |
| **定時／長時間工作**（每日提醒、發電郵、統計） | **獨立一支 Script**（用時間觸發）—— 因為「觸發總執行時間 90 分鐘／日」係同網頁請求分開計，唔會拖累主系統 |
| **網頁前端（doGet／doPost）** | 一支 Script 一個責任；細細隻、易除錯 |

**我哋而家嘅結構已經預留咗呢個彈性：**

* 「進度紀錄」嘅後端係**一個獨立設定值**（`/exec` 網址）—— 將來要拆，只需將「進度追蹤／其他獎章／活動履歷」嗰幾張分頁搬去第二張 Sheet ＋ 第二支 Script，
  再喺「進度 → 設定」換個網址就得，**主系統一行 code 都唔使改**
* 主系統其他分頁（帳目、物資、通告、會議…）照留喺原本嘅 Sheet
* 所以：**要爆都只會爆一邊，唔會攬炒**；亦可以逐件搬，唔使一次過重寫

---

## 7. 一句總結

免費帳號對「一個旅團」嘅用量**綽綽有餘**：6 分鐘／次嘅執行上限，我哋每次只用 1–3 秒；
90 分鐘／日嘅觸發配額，我哋完全冇用；同時執行上限 30，我哋已經用 `LockService` 排隊保護。
如果將來要應付「幾百人同時撳」或者「跨旅團共用一支 Script」，先需要升級 Workspace 或者加快取。
