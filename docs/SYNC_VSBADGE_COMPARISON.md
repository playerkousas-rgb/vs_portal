# 同步排查：vsbadge 與 vs_portal（v2.8.3）

> 比對對象：`playerkousas-rgb/vsbadge` 的 `main`（檢視時 HEAD `98f176b`）。
> 本文件是**程式碼比對與本機模擬測試**，不是正式 Google Sheet／Vercel 環境的實測結果。只取得公開 Registry 診斷（變數是否存在），沒有取得 Key 值、正式執行紀錄或試算表寫讀結果，因此不能宣稱現場故障只有單一原因，亦不能宣稱已替正式站完成部署。

## 為何 vsbadge 看似正常，這個系統卻常常「有寫入、讀不返」？

| | vsbadge | vs_portal（修正前） |
| --- | --- | --- |
| 儲存單位 | `handleSave` 按 `ymis + itemId` 更新／新增「進度追蹤」的一筆紀錄；其他操作也多為特定工作表的紀錄 | 將整份系統資料拆成多張 JSON 表或多段 blob；讀取、報表、帳戶、鏡像都依賴資料庫重建 |
| 驗證 | 伺服器 Registry 必須有後端網址、API Key、名稱；登入／操作需要 token，寫入按權限驗證 | `status` 不需 Key，可能顯示連通，但 `dbInfo`／寫入需要 Key；過期的瀏覽器 Key 曾蓋過正確的伺服器 Key |
| 並發 | 局部更新；部分動作使用 GAS lock（不是「完全無鎖」） | 前端讀版後再寫，舊版 `saveTables` 沒有在後端鎖內比較 `baseVersion`，兩部裝置可能互蓋 |
| 讀取損壞 | 單筆資料出問題通常不必重建整份資料庫 | 曾把讀不到的表跳過，仍回傳部分資料作「完整資料庫」；下次儲存可能把其他資料洗掉 |

**這不是把 vsbadge 的程式直接複製過來便能修好。** 兩者資料模型不同：本系統的帳目、名冊、通告等並非獨立可完全還原的單列；「資料表」與「資料庫」兩種路線及報表鏡像要對準同一份正本。

## 這次確認並修正的程式問題

1. **Key 來源錯置**：`api/proxy.js` 曾只在瀏覽器沒有提供 Key 時才注入伺服器 Key；舊本機設定帶錯 Key 時讀寫被拒。現在代理一律採用 Registry Key，直連 `/exec` 才用使用者自行設定的 Key。
2. **假成功／部分成功**：`saveTables` 曾靜默略過非法、過大的表；現在整批先驗格式，寫入後按版本和各表內容驗收，未齊不刪舊版且不報成功。舊 `saveDb`／分件提交鏡像失敗也不再報成功。
3. **版本與讀回錯亂**：同一毫秒的隨機版本尾碼不能作新舊依據；表格縮短後更不能用「段數較多」當作「較新」。版本已改成單調遞增，讀取／修復以實際較新且可解析的版本為準，損壞的較新表會明確標記。
4. **兩部機互蓋**：新版逐表寫入在 GAS lock 內核對 `baseVersion`；撞版時前端重新拉取並三方合併。分件後備寫入也改用同一個正本版本核對。
5. **損壞資料混入**：讀取發現壞表會拒絕把部分資料當成完整正本；本機 pending 保留待修復。寫入途中本機又有修改也不再在收到成功後直接清走新改動。
6. **舊版後端**：如後端沒回 `confirmed`，前端會讀回並核對每張剛寫的表，對不上就保留 pending；不是見到 `success` 就當真的已同步。

## v2.8.3：旅團編號 `0082` 不可變成數字 `82`

在 v2.8.2 的正式 Sheet 實測，「連線測試」回報「測試行已寫入，但讀回內容不一致」。Google Sheet 的自動格式可能將前導零的旅團編號 `0082` 寫成數字 `82`。原測試會因此失敗；更嚴重的是「資料表」和「資料庫」逐表／後備儲存也用旅團欄作讀回索引。本地 GAS VM 增加數字自動轉型模擬後，重現了測試行、正式逐表、後備寫入同時失敗，讀取找不到資料。v2.8.3 在每次正式寫入之前先把旅團欄設為**純文字**，並明確核對旅團欄和測試記號欄。測試不會把失敗偷偷當成功，亦不需要清除舊資料。

這項修復**必須重貼並重新部署 v2.8.3 的 `apps-script/Code.gs`**（管理部署作業 → 編輯 → 選「新版本」）；只更新 Preview 前端沒有用。重新測試時後端版本應為 **v2.8.3**，再用兩部乾淨裝置驗正式資料。若新測試仍不一致，錯誤會指出是旅團編號欄還是測試記號欄，便於再查。

## 新資料／多人驗收（舊資料不是上線前提）

正式站 `https://vs-portal-pi.vercel.app` 在 2026-09-25 仍提供 **APP v2.8.1**；`/api/units?diag=1` 顯示 0082 已設定後端網址和伺服器端 Key，但只表示變數存在、網址外形合理，**不代表 Key 與 GAS 配對或 Sheet 可以寫入**。本 repo 的修正和以下按鈕尚未部署到正式站；不要以正式站現時的 `status`／`backendReady` 作成功依據。

1. **更新兩端**：把這個分支的前端／Vercel 代理部署到目標環境；將 `apps-script/Code.gs` 貼到**該旅團試算表綁定**的 Apps Script，建立「新版本」並重新部署現有 `/exec`。不要只更新 Vercel。登入頁及測試結果均應顯示 v2.8.3；如現場仍是 v2.8.1／v2.8.2，就還未測到新版。
2. **配對 Key**：平台端 `TROOP_<編號>_BACKEND` 必須是這個部署的正式 `/exec`；`TROOP_<編號>_APIKEY` 必須跟該腳本的 `showApiKey()` 相同。不要把 Key 放在聊天、Issue 或公開前端；伺服器代理會注入 Key，前端本機舊 Key 不能覆蓋它。沒有 Key 時，公開名單的 `backendReady` 不再顯示「可同步」。
3. **先做一寫一讀**：選擇旅團，登入後按頂部「**儲存到後端**」——寫入後收據會立即把結果讀回核對（試算表名稱、筆數、後端版本），「寫咗」同「後端而家有冇」一次過驗。Key 錯誤、Sheet 不能寫或讀回不同都不得當作通過。舊版 GAS 不認識 `syncCheck` 就必須先重新部署。**成功只代表此後端接線及 Sheet 可讀寫，不代表主資料庫已成功儲存。**（舊版「測試寫入＋讀回」「後端實況」按鈕已於 2026-09-26 移除，一寫一讀收據就是驗收入口。）
4. **新帳號及多人測試**：如果是空白旅團，先在所屬 Sheet 的 Apps Script 執行 `initializeSheets()`，接著 `issueSetupKey()`，在登入頁「新旅團開團 KEY」進入，建立首名團長及另一名領袖。按**頂部「儲存到後端」**（其他改動只暫存本機）；換一部全新裝置／無痕視窗，以第一個人的電郵及密碼登入，核對兩名人員；由第二人修改一筆無關緊要的新資料，再按頂部儲存；第三部乾淨裝置以第二人帳號登入，核對新資料。登出／關閉視窗不會自動上載。本機測試不等於此正式驗收。
5. **失敗時先定位，不要盲目清資料**：試寫不過 → 查 GAS 部署版本、試算表名稱及 Key；試寫過但儲存失敗 → 查 `saveTables` 的錯誤、版本衝突及 `baseVersion`；寫入回應成功但新裝置讀不到 → 查同旅團／同後端、實際資料表讀回及登入結果。舊資料不是上線前提，毋須為了驗收先修復；但**不代表可直接刪除正式資料或執行強制覆蓋**。若需要保留現場資料，請先自行備份再作破壞性操作。

本次本機驗證：`npm run check` 通過（含真 `Code.gs` VM＋同源 HTTP 代理的一寫一讀、全新裝置建立帳號／登入／兩人儲存）及全套回歸。**正式站尚未經此對話部署或 POST 寫讀驗收**；仍須現場部署與真 Google Sheet 驗證。與先前產品決定相同：只按頂部「儲存到後端」才上載正式資料，不自動儲存。
